01 / EXTERNAL VALIDATION
# Use your platform URL; login prompts for a password
fedcare auth login \
  --api-url https://your-platform.example/api/v1 \
  --email you@example.org

fedcare task pull TASK_ID
fedcare task schema-check TASK_ID --data ./site_a.csv
fedcare task validate TASK_ID --data ./site_a.csv

# Inspect what will leave the site
fedcare task preview-submit TASK_ID
fedcare task submit TASK_ID

Replace the platform URL, email, TASK_ID, and local path.

Demo part 2 / Federated training

Train here.
Combine there.

Each site starts from the same model and produces a numeric weight archive.

A naming detail

task aggregate runs local training. The owner combines site updates on the platform.

02 / A TRAINING ROUND
fedcare task pull TASK_ID

# Train locally and write numeric weights
fedcare task aggregate TASK_ID \
  --data ./site_a_train.csv \
  --epochs 1 \
  --sample-count-visibility exact

fedcare task preview-submit TASK_ID
fedcare task submit TASK_ID \
  --result-type federated_aggregation_update

# After the owner aggregates: pull the next round
fedcare task pull TASK_ID

Raw data stays local. Submitted weights are visible to the server.

from pathlib import Path
from fedcareai.api import (
    validate_model, train_model, aggregate_updates,
)
from fedcareai.schemas.data_contract import DataContract

contract = DataContract.model_validate_json(
    Path("examples/contract.json").read_text()
)
metrics = validate_model(
    Path("demo/model.joblib"), Path("demo/site_a.csv"),
    contract, "sklearn",
)
train_model(
    Path("demo/model.joblib"), Path("demo/site_a.csv"),
    contract, "sklearn", Path("demo/python_site.npz"),
)
aggregate_updates(
    [Path("demo/python_site.npz")],
    Path("demo/python_average.npz"),
)

03 / Designed for healthcare research

The difference is
in the workflow.

A clinician-facing research process,
with Python doing the local work.

Guided setup

Research questions first.

Create a project, choose a task, upload a model, invite collaborators.

Explicit expectations

A shared data contract.

Declare the target and ordered features instead of leaving assumptions implicit.

Less custom plumbing

One repeatable flow.

Pull, check, run, preview, submit. Local Python setup is still needed.

Make the assumptions executable

Agree the schema.
Check it locally.

Columns. Types. Target.
Feature order. Prediction type.

✓

age, bmi, outcomeMatches the contract

!

age, body_mass_index, outcomeMissing expected column: bmi

EXAMPLES / CONTRACT.JSON
{
  "input_type": "tabular",
  "target_column": "outcome",
  "prediction_type": "classification",
  "metric": "accuracy",
  "columns": [
    {"name": "age", "dtype": "float"},
    {"name": "bmi", "dtype": "float"},
    {"name": "outcome", "dtype": "int"}
  ]
}

The model uses the declared feature order, not the CSV's order.

Challenges → engineering choices

The hard part is
the whole workflow.

The challengeThe design response

Browser ≠ local execution

A web workspace for coordination. Python at each site.

Incompatible inputs

Fail early, before validation or training.

Permissions & traceability

Project membership, task rounds, submission records, checksums.

Reporting honestly

A mean of site metrics is not a pooled patient-level result.

What to take away

Local data.
Shared learning.
Explicit boundaries.

Move trusted models
and agreed outputs.

Treat contracts
as part of the workflow.

Measure generalisation.
Keep governance in place.

Keeping data local does not guarantee private updates. This implementation does not provide differential privacy or cryptographic secure aggregation.
